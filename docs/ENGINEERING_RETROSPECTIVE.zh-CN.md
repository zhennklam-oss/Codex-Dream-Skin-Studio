# Codex Dream Skin Studio 工程技术复盘

> 文档基线：App 0.1.0、Engine 1.6.0、Theme schema 4。本文既是公开技术复盘，也是后续改动必须参照的工程约束。

## 摘要

Codex Dream Skin Studio 大量使用了 AI。AI 参与需求分析、编码、测试和文档工作，但没有仅凭一句长提示词就“生成完成”。需求批准、操作权限、用户数据边界、测试标准和发布条件持续约束着实现。

这里所说的专业开发，和开发者是不是科班出身、是否使用提示词无关。关键在于：AI 的产出能否受到规格、测试、证据、权限边界、数据保护和发布流程的约束。约束不会让软件免于缺陷，却能让结论可复查，让失败更容易复现，也让后续维护者知道哪些边界不能随意越过。

本项目从给 Codex 注入背景图片的脚本，逐步发展为 Tauri 2 桌面应用：它管理主题、预览图像效果、控制皮肤生命周期，并把经过验证的引擎和 Node.js 运行时装入安装包。产品范围及非目标记录在 [PRODUCT.md](../PRODUCT.md)，第三方依赖与许可记录在 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)。

## 项目如何从脚本变成桌面应用

最初的开源项目解决的是“能否换肤”：脚本通过 Codex 的本机调试接口注入样式。实际使用很快暴露出另一组问题：普通用户如何选图、调节位置、保存主题、暂停皮肤、恢复官方外观；应用关闭与彻底退出如何区分；目标电脑找不到 Node 或 Codex 时如何解释；安装包怎样在另一台电脑上独立运行。

因此，工作重心从包装几个脚本，转向建立一条完整控制链：React 负责界面和即时预览，Tauri/Rust 负责桌面窗口、托盘、进程和受管文件，引擎负责连接 loopback CDP 并注入样式。安装包携带引擎资源以及经过验证的 Node.js 24.18.0，不再依赖开发机目录。

功能也经过主动收缩。早期的“四区域”调节看似精细，却无法稳定对应 Codex 的真实 DOM；模拟右栏和内容避让区的预览也制造了超过实际能力的期待。这些功能后来被删除或简化。产品界面只保留引擎能够可靠兑现的控制，这一点比控件数量更重要。

## 它与无约束 vibecoding 的区别

“vibecoding”在本文中指只根据即时观感连续提示、缺少稳定规格和验证门禁的工作方式，并不是对使用 AI 或非专业开发者的贬称。两者真正的差异在工作约束。

| 环节 | 无约束提示词开发的常见风险 | 本项目采用的受约束代理开发 |
| --- | --- | --- |
| 需求 | 需求边做边漂移，旧决定无法追溯 | 先比较方案并取得批准，再把边界写入设计规格 |
| 架构 | 以“界面能点”为完成标准 | 分开界面、Tauri 主进程、注入引擎、用户数据和安装载荷 |
| 实现 | 一次生成大段改动，难以定位回归 | 按计划分阶段改动，控制每阶段的文件和接口范围 |
| 调试 | 根据报错文本猜修复，或增加更长等待 | 先复现和定位根因，再写失败测试并做最小修复 |
| 用户数据 | 重装、迁移或卸载时顺手覆盖目录 | 将主题、图片、设置和未知字段视为必须保留的用户数据 |
| 完成声明 | 界面看似正常便宣布成功 | 只有新鲜测试输出、退出码和产物核对能支持完成声明 |
| 发布 | 将开发目录直接推送 | 清理历史与素材，核对许可、安装载荷、远程下载物和哈希 |

## 实际采用的开发流程

本项目形成的主流程是：用户问题或需求 → 澄清与方案比较 → 用户批准 → 设计规格 → 实施计划 → 分阶段实现 → RED/GREEN → 独立审查 → 完整门禁 → 安装与发布验证。

设计规格回答“做什么、为什么做、什么不做”。实施计划回答“改哪些文件、接口如何变化、测试如何先失败再通过”。两者分开，是为了避免用实施细节偷换已经批准的产品行为。生命周期修复就分别留下了 [docs/superpowers/specs/2026-07-20-runtime-lifecycle-reconciliation-design.md](superpowers/specs/2026-07-20-runtime-lifecycle-reconciliation-design.md) 和 [docs/superpowers/plans/2026-07-20-runtime-lifecycle-reconciliation-implementation.md](superpowers/plans/2026-07-20-runtime-lifecycle-reconciliation-implementation.md)。需求范围发生实质变化时，需要形成新规格并再次批准，而不是悄悄扩大原计划。

实现行为修改时先建立 RED：测试必须能在旧实现上复现问题。修改后进入 GREEN，并继续覆盖相邻的超时、关闭、重入和损坏数据分支。生命周期的仓库级契约位于 [tests/acceptance/runtime-lifecycle-contract.test.mjs](../tests/acceptance/runtime-lifecycle-contract.test.mjs)，引擎级测试位于 [src-tauri/resources/dream-skin-engine/tests/runtime-lifecycle.test.mjs](../src-tauri/resources/dream-skin-engine/tests/runtime-lifecycle.test.mjs)。

阶段完成后审查实际 diff，而不是只听实现者描述。最后再运行跨层验证：前端、Rust、引擎、生命周期、资源清单、安装包和公开快照各自回答不同问题。发布契约见 [tests/acceptance/publication-contract.test.mjs](../tests/acceptance/publication-contract.test.mjs)。

## 使用的 Skill 如何改变工作方式

Skill 在这里是一组工作规则，不是“自动正确”的能力。它们会要求补充证据、延迟编码，或禁止某些省事但高风险的操作。

| Skill / 机制 | 它限制了什么 | 在本项目中的具体结果 |
| --- | --- | --- |
| `brainstorming` | 未澄清目标就直接实现 | 先比较托盘、预览、主题库、运行时与安装方式，并逐项取得批准 |
| `writing-plans` | 把复杂改动塞进一次模糊操作 | 设计规格之后再列文件、接口、测试和提交边界 |
| `test-driven-development` | 修完后才补一个只会成功的测试 | 行为修改先出现可观察的 RED，再实施 GREEN |
| `systematic-debugging` | 根据错误文案直接猜原因 | 沿进程、CDP、WebSocket 和状态机逐层取证，区分症状与根因 |
| `verification-before-completion` | 以“应该好了”代替结果 | 完成声明必须引用本轮运行的测试数、退出码与产物哈希 |
| Tauri / Windows 指南 | 将 Web 思维直接套到桌面生命周期 | 明确窗口 ACL、托盘、隐藏子进程、单实例和 Windows 安装边界 |
| UI/UX 审查 | 让控件数量替代真实能力 | 删除误导性的区域映射，简化预览，补齐字体和无边框窗口交互 |
| 分阶段实现与独立审查 | 同一执行者一次包办实现和结论 | 每阶段检查 diff、测试缺口和用户数据风险，再进入下一阶段 |
| GitHub / Web 发布核验 | 将“已上传”当作“用户下载到相同产物” | 比较公开快照、Release 资产和下载后 SHA-256 |
| `humanizer-zh` | 技术文档堆砌口号和模板句 | 本文在事实稿完成后单独审阅语言，不改动精确标识与数字 |

## 代表性工程案例

### 1. 删除无法兑现的四区域控制

- **最初表现：** 界面允许分别调节左栏、顶栏、主区和底部区域，看起来能一一对应 Codex。
- **工程判断：** Codex 没有向本项目提供稳定的四区域 DOM 契约；按窗口比例切块只是视觉近似。
- **采取的限制：** 找不到可靠选择器和生命周期验证时，不向用户声称区域级定位。
- **结果/证据：** 四区域功能连同旧主题字段和内部区分被删除，改为统一背景参数。

### 2. 简化不真实的预览

- **最初表现：** 预览模拟顶栏、右栏、内容避让区和焦点标，但比例与真实 Codex 重叠，拖动反馈也不一致。
- **工程判断：** 预览擅长表达图片位置和滤镜，无法承诺第三方应用布局的像素级复刻。
- **采取的限制：** 删除右栏、避让区、焦点标和多余阴影，只保留简洁的 Codex 窗口示意。
- **结果/证据：** 预览被明确定位为参数反馈工具，而不是渲染验收截图。

### 3. 对称处理启动与恢复

- **最初表现：** 启动皮肤已经生效却因等待超时报错；恢复官方外观缺少相同等待状态，且一度触发 Codex 反复重启。
- **工程判断：** 超时只说明本次等待没有得到确定答复，不能直接证明操作失败。Start 与 Restore 是相反操作，应共享有界等待、最终状态校准和重入门禁。
- **采取的限制：** 使用统一 deadline，操作结束后重新观察真实状态；门禁阻止并发命令和恢复重启循环。
- **结果/证据：** 设计与实现由上述生命周期规格约束，并由三层生命周期测试持续回归。

### 4. 处理“已安装 Node 仍找不到”的环境问题

- **最初表现：** 另一台电脑安装了新版 Node，应用仍报告 `NODE_NOT_FOUND`。
- **工程判断：** GUI 进程继承的 PATH、版本管理器 shim、注册表和命令行会话可能不同；只执行 `node` 不能证明找到的是可用的 Node。
- **采取的限制：** 验证候选可执行文件的身份与主版本。安装包优先使用私有 Node.js 24.18.0，外部 Node 22+ 只作回退，不修改系统 Node、npm、PATH 或版本管理器。
- **结果/证据：** 系统 Node 和内置 Node 分别运行同一套 26/26 引擎测试，避免把开发机环境当成产品依赖。

### 5. 追查 CDP 超时与 libuv 关闭断言

- **最初表现：** `Page.enable` 偶发超时，成功打开 Codex 后又出现 `UV_HANDLE_CLOSING` 断言。
- **工程判断：** 问题涉及 WebSocket 关闭重入、one-shot 进程退出，以及 `open()` 握手失败时泄漏 session；延长 sleep 不能修复资源竞争。
- **采取的限制：** 用独立子进程复现，检查 code 13 与 unsettled top-level await；为失败路径建立 RED/GREEN，再集中管理关闭和强制退出。
- **结果/证据：** 提交 `02139fa` 修复关闭竞争，`562e4ae` 加固会话握手；子进程测试能在旧实现稳定失败并在修复后通过。

### 6. 发布前停止一次“表面成功”的上传

- **最初表现：** 待公开内容功能完整，但 26 个验证文件包含个人路径或截图，背景素材也没有明确的公开再分发权。
- **工程判断：** `.gitignore` 不能清除已经进入历史的隐私内容；本地可用不等于有权公开分发。发布边界后来写入 [GitHub 发布设计](superpowers/specs/2026-07-21-github-publication-design.md)。
- **采取的限制：** 不直接发布开发历史，移除不可再分发素材，保留上游许可说明，并从受审内容生成干净的单提交公开快照。
- **结果/证据：** `a95308e` 排除个人验证文件，`7e316fa` 移除私有发布素材，`cbc9ba3` 把引擎载荷改为逐字节核对。默认图随后换成上游 MIT 许可覆盖的 Dream Portal，许可来源写在 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)；公开快照为 `09a5e00`。

## 专业限制清单

### 产品真实性

- 只提供引擎能稳定应用的控制，防止 UI 承诺实际不存在的能力。
- 没有稳定 DOM 契约时，不声称能与 Codex 区域一一对应，防止比例模拟被误认为真实定位。
- 明示预览只代表参数效果，不承诺像素级一致，防止用户把示意图当作真实渲染结果。

### Windows 与运行时边界

- 不修改 WindowsApps、官方 `app.asar`、官方二进制或签名，避免破坏更新、签名和系统包完整性。
- CDP 只连接 loopback 地址，并验证目标身份，避免把调试控制暴露到网络或错误进程。
- 隐藏应用启动的子终端，只终止应用自己记录并启动的进程，避免干扰用户的其他 Node 或 Codex 会话。
- 严格区分 Start、Pause、Resume、Restore、关闭到托盘和彻底退出，避免一个按钮暗中执行另一种生命周期操作。

### 用户数据完整性

- 将主题、图片、设置、未知 JSON 字段和损坏文件视为用户数据，禁止用默认值静默覆盖。
- 在受管目录内采用临时文件加原子替换，避免进程中断留下半份配置。
- 引擎同步、重装、恢复与卸载不得删除用户主题，防止维护操作变成数据清除。
- 不覆盖用户工作树的无关改动或本地验证文件，无法安全合并时应停下并说明冲突。

### 环境可移植性

- 不写入开发机绝对路径，所有安装载荷从应用资源目录解析。
- 不盲信 PATH；验证 Node 可执行文件、版本和实际启动结果，防止 GUI 与终端环境差异造成误判。
- 内置 Node 只服务本应用，不替换系统 Node、npm、PATH 或版本管理器，避免影响用户已有开发环境。

### 测试与调试纪律

- 修改行为前先写能在旧实现失败的回归测试，防止测试只是在复述新代码。
- 先定位根因再改代码，禁止用无限 sleep 掩盖竞态；轮询必须使用共享 deadline 和有界等待。
- 覆盖成功、错误、超时、重入、关闭、迁移与损坏数据，避免只验证理想点击路径。
- 真实 Start/Restore 生命周期测试必须通过显式 gate 才能运行，因为它会重启或改变正在使用的 Codex。

### 完成声明与发布纪律

- 没有本轮新鲜输出，不得声称通过或完成；必须记录命令、通过数、失败数和关键产物身份。
- 分阶段实现后审查真实 diff，再运行全量门禁，防止局部测试遗漏跨层变化。
- 分别验证源码、资源清单、安装包、已安装载荷和远程下载包，防止“源码正确”被误当成“用户收到的文件正确”。

### 隐私、版权与开源许可

- 公开前扫描完整历史和发布物，不发布个人路径、截图、缓存、私有验证记录或密钥。
- 没有明确再分发权的素材不得进入仓库或安装包；用户本机选择图片不等于项目获得发布权。
- 保留上游许可证和第三方通知，确保二进制分发仍满足依赖许可义务。

## 后续开发基线

### Definition of Done

一项改动只有同时满足以下条件才能称为完成：范围和权限已确认；相关规格与计划已更新；行为变更具有先失败后通过的测试；用户数据与旧主题兼容；错误、超时、重入和关闭路径已检查；对应层级的全量验证产生新鲜结果；diff、隐私和许可已审查；若交付安装包，则已核对安装载荷和下载文件哈希。任一条件不适用时，应记录具体理由，不能默认为已满足。

### 新功能检查表

- [ ] 用户是否明确授权该功能及其外部影响？
- [ ] 设计规格是否说明目标、非目标、替代方案并已获批准？
- [ ] 引擎是否能真实兑现 UI 中每一个新控制？
- [ ] 实施计划是否列明文件、接口、迁移、测试和回滚边界？
- [ ] 是否先建立了可观察的失败测试？
- [ ] 是否覆盖空状态、错误、超时、取消、重入和关闭？
- [ ] 新字段能否保留旧主题及未知 JSON 字段？
- [ ] 是否在无开发机路径、仅有内置运行时的环境验证？

### Bug 修复检查表

- [ ] 是否记录了最小复现、预期行为和实际行为？
- [ ] 是否用证据定位根因，而非只根据报错文本猜测？
- [ ] 回归测试是否在修复前失败，并且失败原因正是该缺陷？
- [ ] 修复是否避免扩大到未授权的行为或数据迁移？
- [ ] 相邻的超时、错误、重入和关闭分支是否回归？
- [ ] 是否运行了受影响层与仓库契约，而不只是单个测试？

### UI 变更检查表

- [ ] 控件是否对应真实能力，文案是否避免夸大预览精度？
- [ ] 无边框窗口的拖动、最小化、最大化、关闭和键盘焦点是否可用？
- [ ] 中文与英文在所选字体、缩放和窄窗口下是否清晰且不重叠？
- [ ] 加载、等待、成功、失败、禁用和托盘状态是否一致？
- [ ] 动画是否尊重减少动态效果设置，并且不阻断操作？
- [ ] UI 测试是否覆盖命令失败与状态校准，而非只测静态渲染？

### 引擎变更检查表

- [ ] 是否只连接经过验证的 loopback CDP 目标？
- [ ] 是否避免修改 WindowsApps、`app.asar`、官方二进制和签名？
- [ ] 轮询是否共用 deadline，所有等待是否有界？
- [ ] WebSocket、session 和子进程在成功与失败路径都只关闭一次？
- [ ] 是否只终止本应用启动并记录的进程？
- [ ] 系统 Node 与内置 Node 是否运行同一套引擎测试？
- [ ] 真实生命周期测试是否保持显式 gate，且执行已获授权？

### 发布检查表

- [ ] App、Engine、Theme schema 与资源清单版本是否一致且已提升？
- [ ] 全部自动化门禁是否产生本轮通过数和零失败记录？
- [ ] 源码、安装包、已安装载荷和公开下载包是否分别验证？
- [ ] 是否扫描当前树与完整公开历史中的个人路径、截图、密钥和缓存？
- [ ] 所有图片、字体、代码和二进制是否有明确再分发权并保留通知？
- [ ] 是否从受审内容创建干净公开快照，而非直接推送开发历史？
- [ ] 远程下载文件的 SHA-256 是否与获准发布物一致？
- [ ] 发布说明是否准确陈述 Windows、Codex 包、DOM 兼容和预览限制？

这套基线可以随架构演进，但不能被静默绕过。若某条约束不再适用，应通过新证据、规格变更和审查来替换它，而不是在实现中悄悄忽略。
